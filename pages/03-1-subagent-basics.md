# 03-1. Subagent와 멀티에이전트 — 무엇이 다른가

멀티에이전트라고 하면 여러 개의 Claude가 동시에 돌아가는 그림이 떠오릅니다. 맞습니다. 그런데 그 여러 개를 "어떻게 실행하느냐"에 따라 동작 방식이 완전히 달라집니다. 이 장 전체에서 다루는 **네이티브 멀티에이전트**는 Claude Code 하나가 스스로 자신의 분신을 띄우는 방식입니다. TMUX·Redis·별도 터미널이 필요 없습니다. 그냥 대화 한 줄이면 됩니다.

<hr>

## 서브에이전트란 무엇인가 — Agent 도구 개요

Claude Code는 **Agent 도구**(이전에는 Task 도구라고 불렀습니다)로 독립적인 작업 단위인 **서브에이전트(subagent)** 를 실행합니다. 쉽게 말하면 Claude가 또 다른 Claude를 고용해 "나 대신 이 일 해줘"라고 맡기는 구조입니다.

> **명칭 주의**: v2.1.63 이후 공식 명칭은 `Agent` 도구입니다. 구 명칭 `Task`는 하위 호환 별칭(alias)으로 여전히 작동하지만 이 책에서는 "Agent 도구(구 Task 도구)"로 표기합니다.

Claude가 Agent 도구를 호출하면 다음 일이 일어납니다.

1. **새 컨텍스트 창 생성**: 서브에이전트는 완전히 새로운 빈 컨텍스트에서 시작합니다.
2. **위임 프롬프트 전달**: 부모가 Agent 도구 호출 시 작성한 지시문이 서브에이전트의 첫 입력이 됩니다.
3. **독립 실행**: 서브에이전트는 자신의 도구를 써서 작업을 마칩니다.
4. **최종 결과 반환**: 서브에이전트의 마지막 텍스트 출력이 Agent 도구 결과로 부모에게 돌아옵니다.

```
[부모 Claude]
  └─ Agent 도구 호출: "이 파일의 버그를 찾아서 보고해줘"
        │
        ▼
     [서브에이전트]  ← 새 컨텍스트, 독립 실행
       · Read 도구로 파일 읽기
       · 분석 수행
       · 결과 텍스트 반환
        │
        ▼
  [부모 Claude] ← 결과 수신 후 다음 작업 계속
```

**v2.1.198 이후**: 서브에이전트는 기본적으로 백그라운드에서 실행됩니다. 부모 Claude는 서브에이전트가 끝나기를 기다리지 않고 다른 작업을 계속합니다. 서브에이전트가 완료되면 알림이 이후 턴에 도착합니다.

## 격리 컨텍스트 — 왜 분리하나

서브에이전트의 가장 중요한 특성은 **완전한 컨텍스트 격리**입니다. 부모와 자식 사이에는 명시적으로 전달한 것 외에 아무것도 넘어가지 않습니다.

**서브에이전트가 받는 것:**

| 항목 | 설명 |
|---|---|
| 위임 프롬프트 | Agent 도구 호출 시 부모가 작성한 지시문 |
| CLAUDE.md | 계층 구조의 모든 CLAUDE.md 파일 |
| Git status 스냅샷 | 세션 시작 시점의 상태 |
| 서브에이전트 정의 파일 | `.claude/agents/<name>.md`의 시스템 프롬프트 |
| skills 프론트매터 스킬 | 정의 파일의 `skills` 필드에 나열된 스킬 전체 내용 |

**서브에이전트가 절대 받지 않는 것:**

| 항목 | 이유 |
|---|---|
| 부모 대화 이력 | 컨텍스트 창이 별도이므로 부모가 로드한 내용이 상속되지 않음 |
| 부모의 시스템 프롬프트 | 컨텍스트 창이 별도이므로 부모가 로드한 내용이 상속되지 않음 |
| 부모의 메모리·스킬 내용 | 컨텍스트 창이 별도이므로 부모가 로드한 내용이 상속되지 않음 |

이 격리가 오히려 **강점**입니다. 부모의 긴 대화 이력이 없으니 서브에이전트는 깔끔한 컨텍스트로 시작합니다. 복잡한 코드베이스를 탐색할 때 "이전에 다른 파일 얘기를 너무 많이 했더니 혼동한다"는 문제가 사라집니다.

단, 격리는 동시에 **제약**이기도 합니다. 부모가 중간에 쌓은 맥락이나 결정 사항은 위임 프롬프트에 직접 담지 않으면 서브에이전트에 전달되지 않습니다. 서브에이전트에게 일을 시킬 때는 필요한 파일 경로, 오류 메시지, 결정 사항을 위임 프롬프트에 직접 넣습니다.

> ⚠️ **흔한 실수**: "아까 네가 분석한 결과를 보고 처리해줘"라고 서브에이전트에게 시키면 아무것도 모르고 시작합니다. 부모가 그 분석 결과를 위임 프롬프트에 직접 복사해서 넘겨야 합니다.

## 포크 서브에이전트 — 예외적 상속

일반 서브에이전트와 반대로 부모 대화 전체를 물려받는 특수 타입이 있습니다. 바로 **포크(fork)** 입니다.

| | 일반 서브에이전트 | 포크 서브에이전트 |
|---|---|---|
| 컨텍스트 | 완전히 새로운 빈 창 | 부모 대화 이력 전체 |
| 시스템 프롬프트·도구 | 정의 파일에서 | 메인 세션과 동일 |
| 프롬프트 캐시 | 별도 캐시 | 메인과 공유 |
| 생성 방법 | Agent 도구 | `/subtask` 명령(v2.1.212+) |

포크는 "지금까지 대화한 맥락 그대로를 갖고 이 서브 작업만 따로 처리해줘"가 필요할 때 씁니다. 단, 포크 안에서 추가 포크는 불가능합니다.

대부분은 일반 서브에이전트를 씁니다. 포크는 맥락 공유가 반드시 필요한 특수 상황에서만 고릅니다.

## "한 세션 멀티에이전트"의 정의

여기까지 본 내용을 묶으면 네이티브 멀티에이전트의 정의는 다음과 같습니다.

> **네이티브 멀티에이전트**: Claude Code 한 세션이 Agent 도구로 격리된 서브에이전트를 동적으로 생성·실행하는 방식. 별도의 프로세스, 터미널, 네트워크 통신 없이 Claude Code 자체 기능만으로 동작합니다.

이 방식이 4장부터 다루는 **TMUX 기반 분리 CLI 팀**과 어떻게 다른지가 이 장 전체의 핵심 구분선입니다.

| 비교 항목 | 네이티브 멀티에이전트 (3장) | 분리 CLI 팀 (4장~) |
|---|---|---|
| 에이전트 실행 위치 | 한 세션 내부 | 각자 독립 터미널/파인 |
| 역할 지속성 | 호출 시마다 새 컨텍스트 | 세션이 살아있는 한 지속 |
| 설정 방법 | 정의 파일(`.md`) | TMUX + CLAUDE.md + Remote Control |
| 에이전트 간 소통 | Agent 도구 결과 반환 | Redis·pane-send 등 IPC |
| 적합한 규모 | 수십 개 이하 단발 태스크 | 대규모·장기 지속 협업 |

> 🔀 **네이티브 vs 팀 (연결)**: 여기서 세운 구분선은 4-2(팀 레이아웃)·9-3(컨텍스트 관리)의 대비 콜아웃으로 이어집니다.
