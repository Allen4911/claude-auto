# 08-6. 네이티브 vs 팀 — 대비 실전 예제

3장에서 네이티브 서브에이전트를, 4~7장에서 TMUX 기반 분리 CLI 팀을 다루었습니다. 이 절은 그 두 가지를 같은 과제 앞에 나란히 세워 비교합니다. 어느 쪽이 우월한지 가리자는 것이 아니라, 어떤 상황에서 어느 쪽이 자연스러운지 직접 보여 드리려 합니다.

## 같은 과제, 두 가지 방식

### 과제 설정

다음 과제를 두 방식으로 처리합니다.

> **과제**: 레포지토리의 백엔드 4개 모듈(auth, payments, notifications, analytics)에 누락된 JSDoc 주석을 일괄 추가하라. 각 모듈은 독립적이며, 완료 후 전체를 검토해 일관성을 확인한다.

두 방식 다 이 과제를 감당합니다. 다만 선택에 따라 복잡성, 비용, 장기 활용성이 달라집니다.

## 네이티브 서브에이전트로 처리하기

### 설계

각 모듈을 `isolation: worktree` 서브에이전트에게 위임합니다. 4개 서브에이전트가 동시에 돌면서 충돌 없이 각자의 워크트리 브랜치에서 작업합니다.

### 서브에이전트 정의 파일

`.claude/agents/jsdoc-writer.md`:
```markdown
---
name: jsdoc-writer
description: 지정된 모듈 디렉토리의 모든 함수에 JSDoc 주석을 추가합니다.
isolation: worktree
tools: Read, Edit, Glob, Grep, Bash
---

$ARGUMENTS 디렉토리의 모든 TypeScript 파일을 검사하고,
JSDoc 주석이 없는 함수·클래스·메서드에 표준 JSDoc을 추가하세요.

규칙:
- 이미 JSDoc이 있는 곳은 건드리지 않습니다
- @param, @returns, @throws를 빠짐없이 작성합니다
- 타입은 TypeScript 타입 선언과 일치시킵니다
- 완료 후 변경 파일 목록과 추가한 주석 수를 보고합니다
```

### 실행 흐름

부모 세션(메인 Claude)이 4개 서브에이전트를 동시에 위임합니다.

```
메인 세션
│
├─ Agent(jsdoc-writer, "src/auth")       ─┐
├─ Agent(jsdoc-writer, "src/payments")    ├─ 동시 실행 (각자 워크트리)
├─ Agent(jsdoc-writer, "src/notifications")│
└─ Agent(jsdoc-writer, "src/analytics")  ─┘
           ↓ 4개 완료 후
메인 세션 — 결과 수집 → 일관성 검토 → 개발자에게 보고
```

v2.1.198부터 서브에이전트는 기본값이 백그라운드 실행입니다. 메인 세션은 4개를 위임한 뒤 블로킹 없이 다른 작업을 이어갑니다.

### 결과 처리

각 서브에이전트의 워크트리 브랜치(`worktree-jsdoc-writer-1` 등)에 변경이 남습니다. 개발자가 직접 검토 후 병합합니다.

```bash
# 각 워크트리 확인
ls .claude/worktrees/

# 특정 워크트리 내용 확인
cd .claude/worktrees/jsdoc-writer-auth/
git diff main

# 병합 결정 후
git checkout main
git merge worktree-jsdoc-writer-auth
```

### 네이티브 방식의 특징 요약

- **준비 시간**: 정의 파일 하나로 즉시 시작 가능
- **병렬도**: 동시 서브에이전트 기본 20개 한도 내에서 병렬 실행
- **지속성**: 세션이 끝나면 끝. 다음 유사 과제에도 같은 정의 파일을 재사용하지만, 에이전트 간 "경험"은 공유되지 않음
- **결과 병합**: 자동 병합 없음. 개발자가 워크트리 브랜치를 수동으로 검토·병합

## TMUX 팀으로 처리하기

### 설계

같은 과제를 분리 CLI 팀으로 처리합니다. 각 모듈 담당자가 별개 tmux 창에서 독립 Claude Code 세션으로 돌아갑니다. 오케스트레이터가 전체를 조율합니다.

### 팀 레이아웃

```
tmux 세션: jsdoc-project
│
├─ 창 0: 오케스트레이터 (조율·보고)
├─ 창 1: auth-worker     (src/auth 담당)
├─ 창 2: payments-worker (src/payments 담당)
├─ 창 3: notifications-worker (src/notifications 담당)
└─ 창 4: analytics-worker     (src/analytics 담당)
```

### 각 워커 CLAUDE.md

`.claude/workers/auth/CLAUDE.md`:
```markdown
# 역할: auth-worker

담당 범위: `src/auth/` 디렉토리
임무: 이 디렉토리의 모든 TypeScript 파일에 JSDoc 주석 추가

완료 기준:
- JSDoc 없는 함수·클래스·메서드에 @param/@returns/@throws 추가
- 타입은 TypeScript 선언과 일치
- 완료 시 오케스트레이터 pane에 완료 신호 전송

완료 보고: pane-send.sh 0 "auth-worker: 완료. 변경 파일 N개, 주석 M개 추가"
```

### 오케스트레이터 흐름

```bash
# 오케스트레이터가 4개 워커를 순서대로 시작
for worker in auth payments notifications analytics; do
  tmux send-keys -t jsdoc-project:${worker}-worker \
    "claude --dangerously-skip-permissions" Enter
done

# 워커들이 완료 신호를 보내면 일관성 검토 지시
# (모든 워커 완료 후)
claude "각 모듈의 JSDoc 스타일이 일관되는지 src/ 전체를 검토하고 불일치를 보고하라"
```

### 팀 방식의 특징 요약

- **준비 시간**: tmux 세션 설계, 워커 CLAUDE.md 작성, IPC 설정 등 초기 셋업 비용 있음
- **지속성**: 세션을 닫지 않으면 각 워커가 이전 대화 이력을 유지. 연속 작업에서 문맥 축적
- **통신**: 워커 간·오케스트레이터 간 pane-send.sh나 Redis 등으로 명시적 메시지 교환
- **역할 고정**: 각 창의 워커가 특정 역할로 고정되어 반복 과제에 재사용 가능
- **확장성**: 팀 규모를 조절해 더 큰 프로젝트로 확장 가능

## 언제 네이티브 / 언제 팀 / 조합 패턴

### 선택 기준

| 기준 | 네이티브 서브에이전트 | TMUX 팀 |
|---|---|---|
| **준비 비용** | 낮음(정의 파일 하나) | 높음(세션 설계·IPC 설정) |
| **과제 성격** | 명확한 범위의 일회성 병렬 작업 | 지속적·반복적·역할이 고정된 작업 |
| **컨텍스트 누적** | 없음(매 호출 새 컨텍스트) | 있음(세션 내 대화 이력 유지) |
| **에이전트 간 통신** | 없음(부모 통해서만 간접 공유) | 명시적 IPC(pane-send, Redis 등) |
| **결과 병합** | 개발자 수동 | 오케스트레이터가 조율 가능 |
| **비용 예측** | 작업 단위로 명확 | 세션 유지 비용 포함 |
| **설정 공유** | git 커밋으로 팀 전체 동일 | 각 팀원 환경 동기화 필요 |

### 네이티브가 적합한 경우

- 오늘 처음 필요한 일회성 병렬 작업
- 에이전트 간 통신이 필요 없는 독립 작업 묶음
- 정의 파일 하나로 즉시 시작하고 싶은 상황
- 팀 공유보다 빠른 실험이 우선인 경우

**예시**: 전체 레포 린트 일괄 수정, 여러 파일에 걸친 리팩터, 병렬 테스트 생성.

### 팀이 적합한 경우

- 매일 반복 실행하는 업무 흐름(CI 보조, PR 리뷰 자동화)
- 에이전트가 이전 대화 이력을 기억해야 하는 연속 작업
- 에이전트 간 실시간 메시지 교환이 필요한 협업
- 팀 전체가 동일한 역할 구성으로 작업해야 하는 경우

**예시**: 24시간 모니터링 봇, 지속 PR 검토 팀, 역할 고정 개발 팀.

### 조합 패턴 — 두 방식을 함께

두 방식은 경쟁이 아니라 계층을 이룹니다. 팀 오케스트레이터가 네이티브 서브에이전트를 위임하는 구조가 가장 흔한 조합입니다.

```
TMUX 팀 (지속 역할, IPC)
│
├─ 오케스트레이터 세션
│    └─ 대규모 분석 태스크 발생 시
│         ├─ Agent(isolation: worktree) ─┐
│         ├─ Agent(isolation: worktree)  ├─ 네이티브 병렬 처리
│         └─ Agent(isolation: worktree) ─┘
│              ↓ 결과 반환
│         오케스트레이터가 수집·종합·팀에 배분
│
├─ backend-worker 세션 (지속)
└─ frontend-worker 세션 (지속)
```

조합 시 역할 분리 원칙:

- **TMUX 팀**: 역할·상태·통신이 필요한 지속적 조율
- **네이티브 서브에이전트**: 팀이 내린 결정을 실행하는 단발성 병렬 처리

팀은 역할을 지속시키고, 서브에이전트는 병렬 처리를 맡습니다. 한 방식만으로 감당하기 어려운 대규모·복합 작업에 잘 맞습니다.

---

이 절로 네이티브 멀티에이전트(3장)와 팀 기반 협업(4~7장)이 하나의 그림으로 이어집니다. 도구 선택은 결국 과제의 성격에 달렸습니다. 정의 파일 하나로 빠르게 병렬 처리할 일이면 네이티브가 맞고, 역할이 고정된 지속 협업이 필요하면 팀이 맞습니다. 둘 다 필요하면 조합입니다.
