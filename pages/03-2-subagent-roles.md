# 03-2. 역할별 Subagent 설계 — Planner·Dev·Reviewer

서브에이전트는 만들기 쉽습니다. 잘 만들기는 별개입니다. "그냥 Claude에게 시키면 되지 않냐"와 "Planner·Dev·Reviewer 역할을 나눠서 쓴다"의 차이는 프로젝트가 커질수록 뚜렷해집니다. 이 절에서는 역할을 파일로 정의하는 방법과 상황별로 어떤 역할을 띄울지 알아봅니다.

<hr>

## 서브에이전트 정의 만들기 — 자연어 요청과 직접 편집

서브에이전트 정의 파일은 직접 써도 되고, Claude에게 만들어달라고 요청해도 됩니다.

> **버전 참고 — `/agents` 명령어의 변화**: v2.1.197 이하에서는 `/agents` 슬래시 명령어가 대화형 인터페이스를 열었습니다. v2.1.198 이후에는 이 인터페이스가 제거되어 정의 파일을 직접 작성하거나 Claude에게 요청하는 방식이 공식 권장 방법이 되었습니다.

가장 빠른 방법은 Claude에게 직접 부탁하는 것입니다.

```
코드 리뷰 전담 서브에이전트를 만들어줘.
.claude/agents/code-reviewer.md에 저장하고,
도구는 Read·Glob·Grep만 허용하고 모델은 sonnet으로 설정해줘.
```

Claude가 프론트매터와 시스템 프롬프트까지 채운 파일을 만들어 줍니다. 생성된 파일을 열어 확인하고 필요한 부분만 고칩니다.

Claude Code는 `.claude/agents/`와 `~/.claude/agents/` 디렉터리를 감시합니다. 파일을 추가하거나 수정하면 재시작 없이 몇 초 안에 자동 반영됩니다. 디렉터리 자체를 처음 만들 때만 재시작이 필요합니다. 하위 폴더까지 재귀적으로 스캔하므로 역할별로 폴더를 나눠 관리해도 됩니다. 에이전트 식별자는 파일명이 아니라 프론트매터의 `name` 필드 기준입니다.

현재 사용 가능한 서브에이전트 목록은 v2.1.224 이상에서 `/list-agents` 명령어로 확인합니다.

### description 필드 — 위임 판단의 근거

`description` 필드는 오케스트레이터 Claude가 "이 작업을 어느 에이전트에 맡길까"를 판단할 때 가장 먼저 읽는 단서입니다. 사람이 팀원에게 일을 넘길 때 직함보다 "이 사람이 어떤 상황에서 호출받는 사람인가"를 보듯, 오케스트레이터도 이 필드에서 에이전트의 역할 경계를 읽습니다. 그래서 "무엇을 한다"는 기능 설명만으로는 부족합니다. "어느 시점, 어떤 조건에서 호출되어야 한다"는 호출 조건까지 함께 담겨야 위임이 정확해집니다.

실무에서 이 차이는 금방 드러납니다. `description: 코드를 리뷰합니다`만 적혀 있으면 오케스트레이터는 버그 분석 요청도, PR 정책 검토 요청도 이 에이전트로 보냅니다. 반면 `Dev 에이전트의 코드 변경이 완료된 후 리뷰가 필요할 때 호출합니다`처럼 호출 시점을 못박아 두면 Planner 단계나 설계 논의 중에 이 에이전트가 끼어들 일이 없습니다. 에이전트가 많아질수록 description을 얼마나 정밀하게 쓰느냐가 워크플로 전체의 안정성을 좌우합니다.

```yaml
# 낮은 정확도: 무엇을 하는지만 설명
description: 코드를 리뷰합니다.

# 높은 정확도: 언제 호출할지 명시
description: >
  코드 품질·보안·성능 이슈를 검토합니다.
  Dev 에이전트의 코드 변경이 완료된 후 리뷰가 필요할 때 호출합니다.
```

### 도구 권한과 모델 지정

도구 제한은 에이전트의 역할 경계를 런타임에서 강제합니다. 시스템 프롬프트에 "절대 파일을 수정하지 마세요"라고 적어도 모델이 충분히 확신하면 그 지시를 어길 수 있습니다. 반면 `tools: Read, Glob, Grep`처럼 허용 목록을 명시하면 `Write`와 `Edit`는 해당 에이전트 인스턴스에서 실행 자체가 막힙니다. Reviewer가 직접 파일을 고치거나 Planner가 의도치 않게 코드를 바꾸는 사고는 도구 제한이 없을 때 일어납니다.

`tools`(허용 목록)와 `disallowedTools`(거부 목록)는 쓰임새가 다릅니다. 허용 목록은 쓸 도구가 명확히 고정된 에이전트에 맞습니다. 읽기 전용으로 탐색·분석만 하는 에이전트처럼 범위가 좁으면 그만큼 강한 제약을 걸 수 있습니다. 거부 목록은 기본 도구 세트에서 위험한 도구만 골라 막을 때 씁니다. 거의 모든 도구가 필요하지만 파일 삭제만큼은 절대 허용하면 안 되는 경우처럼요. 둘 다 지정하면 `disallowedTools`가 먼저 적용됩니다.

```yaml
tools: Read, Glob, Grep       # 이 도구만 허용, 나머지 전부 차단
disallowedTools: Write, Edit  # 이 도구만 차단, 나머지 허용
```

`model` 필드는 에이전트 성격에 맞는 모델을 붙여 주는 라우팅 설정입니다. 필드를 생략하거나 `model: inherit`으로 적으면 메인 대화에서 쓰는 모델을 그대로 씁니다. 앨리어스(`opus·sonnet·haiku·fable`)나 전체 모델 ID(`claude-opus-5`)를 적으면 됩니다.

역할별 패턴이 있습니다. 아키텍처를 설계하고 복잡한 트레이드오프를 따지는 Planner에는 추론 능력이 높은 `opus`가 맞습니다. 코드를 쓰는 Dev, 기준에 따라 검토하는 Reviewer는 속도와 품질이 균형을 이루는 `sonnet`이 실용적입니다. 파일 목록 수집, 특정 패턴 탐색, 단순 요약처럼 반복적이고 기계적인 일은 `haiku`로 보내면 비용이 크게 내려갑니다. 서브에이전트를 열 개 띄우면서 전부 `opus`를 쓴다면 비용은 순식간에 올라갑니다. 작업 성격에 맞게 모델을 나눠 쓰는 것이 실무에서 멀티에이전트 비용을 관리하는 핵심입니다.

> 💡 **03-1 연결**: 서브에이전트가 시작될 때 어떤 정보를 받는지(위임 프롬프트, CLAUDE.md, 정의 파일)와 받지 않는지(부모 대화 이력, 부모 시스템 프롬프트)의 전체 목록은 **03-1** '격리 컨텍스트' 절에서 확인합니다.

## 서브에이전트 정의 방식

서브에이전트를 정의하는 방법은 세 가지입니다. 실무에서는 마크다운 파일 방식을 가장 많이 씁니다.

### A. 마크다운 파일 (가장 일반적)

`.claude/agents/` 디렉터리 안에 `.md` 파일을 만들면 됩니다. 파일 이름이 에이전트 이름이 됩니다.

```markdown
---
name: code-reviewer
description: 코드 품질·보안·성능 이슈를 검토합니다. 코드 변경 완료 후 리뷰가 필요할 때 호출합니다.
tools: Read, Glob, Grep
model: sonnet
---

당신은 시니어 코드 리뷰어입니다.
변경된 파일을 분석하여 품질·보안·성능 이슈를 찾아 보고합니다.
수정 제안은 구체적인 코드 예시와 함께 제시합니다.
```

파일 저장 위치는 우선순위 순으로 다음과 같습니다.

| 위치 | 경로 | 적용 범위 |
|---|---|---|
| 조직 관리(Managed) | 관리자 설정 | 조직 전체 |
| 프로젝트 | `.claude/agents/<name>.md` | 이 프로젝트만 (버전 관리 가능) |
| 개인 전역 | `~/.claude/agents/<name>.md` | 내 모든 프로젝트 |

팀과 에이전트 정의를 공유하려면 `.claude/agents/`에 파일을 두고 git으로 커밋합니다.

### B. SDK 프로그래밍 방식

`query()` 함수의 `agents` 파라미터에 `AgentDefinition` 객체를 전달합니다. 이름이 같다면 프로그래밍 정의가 파일 기반 정의를 덮습니다. 코드로 에이전트를 동적으로 생성해야 할 때 씁니다.

### C. 내장(빌트인) 서브에이전트

Claude Code에 기본 탑재된 에이전트들도 있습니다.

| 이름 | 용도 |
|---|---|
| `Explore` | 읽기 전용 코드베이스 탐색 |
| `Plan` | 플랜 모드 리서치 |
| `general-purpose` | 복잡한 다단계 작업 |

이 내장 에이전트들은 별도 파일 없이 바로 호출합니다.

## Planner·Dev·Reviewer 역할 프롬프트 설계

한 세션 안에서 여러 서브에이전트를 역할별로 나누면 각자 맡은 영역에만 집중합니다. 실무에서 자주 쓰는 3역할 패턴을 소개합니다.

### Planner — 계획 수립 에이전트

```markdown
---
name: planner
description: >
  요구사항을 분석해 구현 단계를 설계합니다.
  새 기능 구현 전, 버그 원인 파악 전에 호출합니다.
tools: Read, Glob, Grep
model: opus
---

당신은 소프트웨어 아키텍트입니다.
주어진 요구사항을 분석하여 구체적인 구현 계획을 작성합니다.

계획 출력 형식:
1. 현재 코드베이스 분석 결과
2. 구현 단계 목록 (각 단계별 예상 파일·함수·변경 범위)
3. 주의해야 할 의존성·리스크
4. 검토가 필요한 기존 코드 위치

코드를 직접 작성하지 않습니다. 계획만 제시합니다.
```

**설계 포인트**: Planner는 `Read·Glob·Grep`만 허용하고 `Edit·Write`를 제외합니다. 파일 탐색과 분석에만 집중하고 실수로 코드를 변경하는 일을 원천 차단합니다. 무거운 `opus` 모델을 써서 분석의 질을 높입니다.

### Dev — 구현 에이전트

```markdown
---
name: dev
description: >
  코드를 실제로 작성·수정합니다.
  Planner의 계획을 받아 구현할 때 호출합니다.
tools: Read, Write, Edit, Bash, Glob, Grep
model: sonnet
---

당신은 시니어 개발자입니다.
전달받은 구현 계획에 따라 코드를 작성합니다.

작업 원칙:
- 계획에 명시된 파일과 범위에만 집중합니다.
- 변경한 파일 목록과 변경 내용 요약을 반드시 보고합니다.
- 계획 범위를 벗어나는 발견 사항은 직접 수정하지 않고 보고합니다.
```

**설계 포인트**: Dev는 실제 파일을 변경하므로 `Write·Edit·Bash`가 필요합니다. `sonnet` 모델로 속도와 비용의 균형을 맞춥니다. 계획 범위를 벗어난 수정을 금지하는 규칙이 중요합니다. 이 규칙이 없으면 Reviewer가 예상 밖의 변경까지 검토해야 합니다.

### Reviewer — 검토 에이전트

```markdown
---
name: reviewer
description: >
  변경된 코드를 검토하고 이슈를 보고합니다.
  Dev 작업 완료 후 호출합니다.
tools: Read, Glob, Grep, Bash
model: sonnet
---

당신은 코드 리뷰 전문가입니다.
변경된 코드를 아래 기준으로 검토합니다.

검토 기준:
1. 버그 가능성: 엣지 케이스, 널 처리, 경계값
2. 보안: 입력값 검증, 민감 정보 노출
3. 성능: 불필요한 반복, N+1 쿼리
4. 가독성: 네이밍, 복잡도

각 이슈는 파일명:줄번호와 함께 보고합니다.
심각도는 CRITICAL·MAJOR·MINOR로 구분합니다.
```

**설계 포인트**: Reviewer는 `Write·Edit`를 제외하고 읽기 전용 도구만 씁니다. 리뷰어가 직접 코드를 고치면 검토와 구현이 섞여 책임이 불분명해집니다. `Bash`는 테스트 실행에 필요합니다.

## 언제 어떤 역할을 띄우나

역할 분담의 실익은 맹목적인 병렬화가 아닙니다. 각 단계의 목적에 맞는 도구와 모델을 쓴다는 점입니다.

### 순차 의존 작업 — Planner → Dev → Reviewer

```
요구사항 입력
    │
    ▼
[Planner] ── 계획 문서 ──▶ [Dev] ── 코드 변경 ──▶ [Reviewer]
                                                        │
                                                   이슈 보고
                                                        │
                                              심각도에 따라 재작업 여부 결정
```

이 흐름은 단순하지만 효과적입니다. Planner가 분석을 끝내야 Dev가 시작할 수 있으므로 순차 실행이 맞습니다.

### 독립 작업 — 병렬 Dev

파일 A 수정과 파일 B 수정이 서로 의존성이 없다면 두 개의 Dev 에이전트를 동시에 띄울 수 있습니다.

```
[Dev-A] 파일 A 수정  ─┐
                        ├─▶ [Reviewer] 결과 통합 검토
[Dev-B] 파일 B 수정  ─┘
```

병렬 실행은 빠르지만 비용도 함께 늘어납니다. 독립성이 확실하지 않은 작업을 병렬로 돌리면 서로 같은 파일을 건드리는 충돌이 생깁니다. 돌리기 전에 작업 간 의존성을 꼭 확인하세요.

### 언제 역할을 나누지 않아도 되나

작업 규모가 작고 단발성이라면 역할 정의 파일 없이 그냥 Agent 도구에 상세한 지시문을 넣어도 충분합니다. 역할 분담이 의미 있는 시점은 다음과 같습니다.

- 동일한 역할을 여러 프로젝트에서 반복 사용할 때
- 역할마다 허용 도구를 다르게 제한해야 할 때
- 팀 전체가 같은 에이전트 정의를 공유해야 할 때

> 🔀 **네이티브 vs 팀 (연결)**: 4-4(CLAUDE.md 역할 정의)에서는 "역할이 세션이 살아있는 한 지속된다"는 분리 CLI 팀의 차이를 대비 콜아웃으로 다룹니다. 네이티브에서는 역할 정의 파일이 있더라도 호출할 때마다 새 컨텍스트에서 시작합니다.
