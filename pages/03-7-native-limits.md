# 03-7. 네이티브의 한계, 그리고 팀으로의 전환

이 장에서 배운 네이티브 멀티에이전트는 강력합니다. 한 세션 안에서 설정 없이 서브에이전트를 띄우고 병렬로 작업을 분담하고 결과를 취합할 수 있습니다. 그런데 실제 팀 프로젝트에 적용하다 보면 어느 순간 벽에 부딪힙니다. 그 벽이 어디에 있는지 미리 알아야 막혔을 때 당황하지 않고 다음 도구를 꺼낼 수 있습니다.

<hr>

## 컨텍스트의 한계

서브에이전트의 격리 컨텍스트는 03-1에서 강점으로 소개했습니다. 그 격리가 동시에 가장 큰 제약이기도 합니다.

**누적 맥락을 공유할 수 없습니다.**

프로젝트가 진행되면서 팀 전체가 알아야 할 결정이 쌓입니다. "이 모듈은 레거시 API를 건드리지 않기로 했다", "인증 로직은 A 서비스가 담당한다", "이번 스프린트 범위는 여기까지다" 같은 맥락입니다. 분리 CLI 팀에서는 각 에이전트가 자신의 CLAUDE.md에서 이 맥락을 세션 내내 유지합니다. 네이티브에서는 위임 프롬프트에 매번 다시 써서 넘겨야 합니다.

작업 하나라면 괜찮습니다. 그런데 수십 개의 서브에이전트가 같은 맥락을 공유해야 하는 상황이라면 위임 프롬프트가 길어지고 중복이 쌓이고 맥락 전달 실수가 생기기 마련입니다.

**컨텍스트 압축이 발생하면 정보가 손실됩니다.**

긴 세션에서 컨텍스트 창이 가득 차면 압축이 일어납니다. 이때 서브에이전트 정의 파일의 설명 등 일부 정보가 압축 대상이 될 수 있습니다. 장시간 실행되는 프로젝트에서 네이티브 멀티에이전트만으로는 맥락을 온전히 보존한다고 장담하기 어렵습니다.

<hr>

## 역할 지속성의 한계

네이티브 서브에이전트의 역할은 호출할 때마다 새로 시작합니다.

Planner 에이전트가 어제 분석한 내용, Dev 에이전트가 지난주에 구현한 결정, Reviewer 에이전트가 한 달 전에 세운 코드 스타일 기준 — 모두 에이전트를 다시 띄우는 순간 사라집니다. 정의 파일에 적혀 있는 것만 남습니다.

실제 팀에서 시니어 개발자의 가치는 코딩 실력만이 아닙니다. "이 프로젝트에서 왜 이 결정을 했는지", "이전에 비슷한 시도를 했다가 왜 실패했는지"를 기억하는 것이 핵심입니다. 네이티브 서브에이전트는 이 경험의 축적을 유지하지 못합니다.

분리 CLI 팀에서는 에이전트가 CLAUDE.md와 세션 이력에 프로젝트의 역사를 누적합니다. 에이전트는 세션이 살아있는 한 역할과 맥락을 지속합니다.

<hr>

## 규모의 벽

네이티브 멀티에이전트의 동시성 제한은 명확합니다.

| 제한 | 기본값 |
|---|---|
| 동시 실행 서브에이전트 | 최대 **20개** |
| 에이전트 중첩 깊이 | 최대 **3레이어** |

20개는 작은 숫자가 아닙니다. 대부분의 단발 작업에서 이 한도에 부딪히지 않습니다. 하지만 대규모 리팩터링, 수백 개 파일 마이그레이션, 장시간 모니터링이 필요한 작업에서는 한계가 드러납니다.

더 근본적인 문제는 지속적인 협업입니다. 네이티브 서브에이전트는 태스크가 끝나면 소멸합니다. 팀장이 작업자에게 메시지를 보내고 작업자가 진행 상황을 실시간으로 보고하고 팀 전체가 같은 화면에서 동시에 무슨 일이 일어나는지 볼 수 있는 구조는 네이티브로 구현하기 어렵습니다.

에이전트 간 통신도 한계가 있습니다. 네이티브에서는 Agent 도구의 결과 반환이 유일한 소통 수단입니다. 에이전트 A가 작업하는 중에 에이전트 B에게 "지금 당장 이것도 확인해줘"라고 메시지를 보내는 것, 두 에이전트가 공유 상태를 동시에 읽고 쓰는 것은 네이티브로는 자연스럽게 처리할 수 없습니다.

<hr>

## 전환 — 왜 분리 CLI 팀인가

지금까지 세 가지 한계를 살펴봤습니다.

1. **컨텍스트**: 누적 맥락을 매번 새로 전달해야 하고, 장시간 실행 시 손실 위험이 있습니다.
2. **지속성**: 역할이 호출마다 초기화됩니다. 경험이 쌓이지 않습니다.
3. **규모**: 동시 20개 한도, 단방향 결과 반환, 실시간 협업 불가.

이 세 가지가 동시에 필요해지는 시점이 있습니다. 며칠에 걸쳐 진행되는 프로젝트, 5인 이상이 분업하는 대규모 코드베이스, 팀장이 실시간으로 각 에이전트의 상태를 모니터링해야 하는 상황입니다.

바로 이 시점에 TMUX 기반 분리 CLI 팀이 등장합니다.

TMUX는 하나의 터미널을 여러 파인(pane)으로 나눠서 각 파인에 독립 프로세스를 실행합니다. Claude Code 인스턴스를 파인마다 하나씩 띄우면 각 Claude가 자신의 세션과 컨텍스트를 유지하면서 장시간 역할을 지속합니다. Remote Control로 에이전트 간 메시지를 주고받고 Redis로 공유 상태를 관리하면 진짜 팀처럼 협업할 수 있습니다.

```
네이티브 멀티에이전트 (3장)        분리 CLI 팀 (4장~)
─────────────────────────────       ─────────────────────────────────
한 세션 + Agent 도구                TMUX 파인 × Claude 인스턴스 수
역할: 호출마다 초기화               역할: 세션이 살아있는 한 지속
소통: 결과 반환(단방향)             소통: Remote Control + Redis(실시간)
규모: 동시 20개 한도                규모: 파인·인스턴스 수만큼
적합: 단발 태스크, 소규모 분업      적합: 장기 프로젝트, 대규모 협업
```

> 4장에서는 TMUX의 세션·윈도우·파인 구조부터 시작합니다. 이 구조만 이해하면 이후 모든 팀 설정과 자동화 스크립트가 "어느 파인에 어떤 에이전트를 배치하고 어떻게 메시지를 보내는가"라는 하나의 패턴으로 읽힙니다. 네이티브에서 익힌 서브에이전트 개념은 그대로 가져가되, 이제 그 에이전트들이 더 넓고 지속적인 무대에서 움직이게 됩니다.

---

네이티브 멀티에이전트는 버리는 게 아닙니다. 단발 태스크, 빠른 프로토타입, 독립적인 분석 병렬화에서는 여전히 가장 빠른 선택입니다. 도구는 상황에 맞게 쓰면 됩니다. 분리 CLI 팀이 필요한 시점이 언제인지를 지금 배워두면, 그 시점이 왔을 때 자연스럽게 4장의 도구를 꺼낼 수 있습니다.
